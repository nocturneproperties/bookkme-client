# Bookk client web app (`apps/client/`)

`:client` is the Kobweb (Kotlin/JS, Compose HTML + Silk) app for people who book, served on its own host, `https://app.bookkme.com`. Today it is the Telegram Mini App; browser booking will join it later. It is separate from the marketing site (`:site`, `bookkme.com`) so the site's download stays free of the client stack (Koin, Ktor, Room/SQLite WASM, sign-in, the Telegram SDK) and each host can send its own headers: the Mini App must be frameable by Telegram Web, the site need not be.

Read [`apps/site/README.md`](../site/README.md) first: the web design system (`:designsystem`'s `jsMain`), the JS-runtime rules, the DOM API setup and the language model apply here too. The project-wide rules in the root `AGENTS.md` apply as everywhere.

## Commands

- **Run the client app**: `./gradlew :client:kobwebStart -t -Pbuildkonfig.flavor=devDebug` (http://localhost:8081, so it runs next to the site on 8080; the `Client` run configuration passes the same flavor), stop with `./gradlew :client:kobwebStop`.
- **Run JS tests**: `./gradlew :client:jsNodeTest -Pbuildkonfig.flavor=devDebug`.
- **Export as CI does**: `./gradlew :client:kobwebExport -PkobwebBuildTarget=RELEASE -PkobwebExportLayout=FULLSTACK -Pbuildkonfig.flavor=devRelease`.

## Layout

Code in `src/jsMain/kotlin/me/bookk/client/`, copy in `src/commonMain/moko-resources` (`ClientRes`, keys prefixed `client_`; EN with `uk/` and `pl/` like the site, no `ru/`), static files in `src/jsMain/resources/public/`:

- `AppEntry.kt`: the `@App` (Silk, colour mode, `LocalizedContent` with the `ClientRes`, `AuthRes`, `DashboardRes`, `BookingRes` and `SettingsRes` strings). Keep feature string keys unique against `client_`, `DesignSystem` and `CorePresentation` keys and each other, since the merged provider resolves by key alone (the Home screen's keys are prefixed `dashboard_client_home_`).
- `pages/`: thin Kobweb `@Page` files. `Index.kt` (`/`) is the Telegram Mini App entry, the URL to register as the bot's Mini App (BotFather) and Menu Button: `https://app.bookkme.com/`. Its `@InitRoute` shows the preferred language (Kobweb's default while exporting) and starts Koin.
- `layout/ClientPageHead`: title (`<page> · BookkMe`), description and `robots: noindex` through `:designsystem`'s `HeadTags`. The app has no canonical, hreflang or Open Graph tags, no sitemap and no language URL prefixes; `public/robots.txt` disallows everything.
- `navigation/ClientLink`: links out of the app. `ClientLink.siteClients(...)` points at the site's `/clients` page in the current language, on the `SiteUrl` from Koin (BuildKonfig `SITE_URL`, so dev builds link the dev site).
- `telegram/`: `TelegramMiniApp` and `TelegramMessage` (see **Telegram Mini App**).
- `di/ClientApp.kt`: `initClientApp()` (see **Koin**).
- Logos and favicons come from `:designsystem`'s `jsMain/resources/public/` (shared with the site); the app adds no manifest or share image because it is not meant to be installed or linked from search.

## Koin

`initClientApp()` is the web counterpart of `:shared`'s `initBusinessApp`, called from the `@InitRoute` of each page that uses the API (currently `/`). It returns early once Koin is running, so revisiting a page in the same session keeps the existing graph. It installs `:shared:common`'s `initLogging()` and `commonModule()` (the same Ktor client as the apps on the JS engine: protobuf, bearer auth with refresh, `X-Platform`/`Accept-Language` headers; plus `ErrorMapper` and `SiteUrl`), and the web modules that client and Telegram sign-in need: `deviceModule()`, `cacheModule()`, `filesModule()`, `validationModule()` (`ValidateName` and `ValidateEmail` for the booking profile and the email change), `clientDatabaseModule()`, `authDomainModule()`, `authDataModule()`, `settingsDomainModule()`, `settingsDataModule()` (settings provides the legal documents `InitialAppDataFetch` preloads, and its `AppStartAction`, `BackgroundDataFetchAction` and `LogOutAction` bindings join the web fetch and logout), `authPresentationModule()` (its `jsMain` actual binds `WebClientStateFactory`, `WebEmailVerificationStateFactory` as the `EmailVerificationStateFactory` the shared `ChangeEmailViewModel` and `VerifyEmailViewModel` take, and those ViewModels next to the sign-in ones), and for the Home screen `clientAppointmentsDomainModule()`, `clientAppointmentsDataModule()` (`CommonClientBookingDataSource`, a `LogOutAction` that clears the client's bookings and `saved_business`, and `CommonAppointmentRequestDataSource`, which `CreateAppointmentRequest` sends booking requests and `WithdrawAppointmentRequest` withdraws them through; `CommonClientBookingDataSource` also caches each business's note to clients in `ClientDatabase`'s `booking_info` for `GetBookingInfo` and clears it on logout), `clientBusinessDomainModule()` (`GetBusinesses`, the bulk business read), `clientBusinessDataModule()` (`CommonBusinessDataSource`, whose `LogOutAction` clears `business`) and `dashboardPresentationModule()`; for the services step `clientServicesDomainModule()` (`GetBusinessServices`, and `CreateQuote` for the Review step), the full `servicesDataModule()` (its DAOs are in `ClientDaos`, its `LogOutAction`s clear `service`, `service_group` and their prefs), for the specialist step employees' `clientEmployeesDomainModule()` (`GetBookableEmployees`) and `clientEmployeesDataModule()` (`CommonBookableEmployeeDataSource`, caching them in `ClientDatabase`'s `bookable_employee` tables through `bookableEmployeeDao`, a `LogOutAction` that clears them), and booking's `bookingDomainModule()` (`GetBookingCatalog`, `GetBookingPreparation`, `SetBookingServices`, `GetBookingSpecialists`, `SetBookingSpecialist`, `GetBookingTimetable`, `GetBookingSlots`, `SetBookingSlot`, `SendBookingRequest`, `GetBusinessMessage`, `GetSentBooking`, `GetBookingRequestDetails`, `GetBookingAppointmentDetails`, `WithdrawBookingRequest`; `GetBusinessMessage` wraps `clientAppointmentsDomainModule()`'s `GetBookingInfo`, `GetBookingSlots` wraps `clientAppointmentsDomainModule()`'s `GetFreeSlots`, `SendBookingRequest` wraps services' `CreateQuote` and `clientAppointmentsDomainModule()`'s `CreateAppointmentRequest` and `GetUpcomingBookings`, `GetSentBooking` wraps `GetUpcomingBookings`, `GetBookingRequestDetails` and `GetBookingAppointmentDetails` wrap `clientAppointmentsDomainModule()`'s `GetClientAppointmentRequest` and `GetClientAppointment` (one cached request or appointment by id, any status), `WithdrawBookingRequest` wraps `clientAppointmentsDomainModule()`'s `WithdrawAppointmentRequest` and `GetUpcomingBookings`), `bookingDataModule()` (`InMemoryBookingPreparationDataSource`, the one datasource behind every booking step: a `single` and `LogOutAction` holding the approved services, specialist and time per business) and `bookingPresentationModule()` (`BookingServicesViewModel`, `BookingSpecialistViewModel`, `BookingDateTimeViewModel`, `BookingReviewViewModel`, `BookingSentViewModel`, `BookingRequestDetailsViewModel`, `BookingAppointmentDetailsViewModel` and `WebBookingStateFactory`), and `settingsPresentationModule()` (its `jsMain` actual binds `WebSettingsStateFactory` as the `SettingsStateFactory` and registers only the settings ViewModels that have a web screen, today `SettingsDashboardViewModel` and `EditProfileViewModel`). `BookingDateTimeViewModel` also takes the `Clock` that `authDomainModule()` binds. The client app installs these client-only modules, not the mobile `appointmentsDomainModule()`/`appointmentsDataModule()`/`businessDomainModule()`/`businessDataModule()`: the full business domain module's `RefreshBusinessInfo` is a `DataFetchAction` that would delete every cached business missing from `/business/mine`, and the full business data module binds DAOs `ClientDatabase` does not have.

Add a web feature's domain and data modules there when the app starts using it, together with whatever its trigger and `LogOutAction` bindings need: `getAll()` builds every bound action, so one unresolvable dependency breaks `InitialAppDataFetch` or `LogOut` for the whole app. `ClientAppTest` checks the graph resolves, including `SignInWithTelegram`, `LogOut`, `SaveBusiness`, `GetBusinesses`, `GetBusinessServices`, `GetBookableEmployees`, the booking use cases (`GetBusinessMessage`, `SendBookingRequest`, `GetSentBooking`, `GetBookingRequestDetails`, `GetBookingAppointmentDetails` and `WithdrawBookingRequest` included), one shared `BookingPreparationDataSource`, `ClientHomeViewModel`, `BookingServicesViewModel`, `BookingSpecialistViewModel`, `BookingDateTimeViewModel`, `BookingReviewViewModel`, `BookingSentViewModel`, `BookingRequestDetailsViewModel`, `BookingAppointmentDetailsViewModel`, `SettingsDashboardViewModel`, `EditProfileViewModel`, `ChangeEmailViewModel` and `VerifyEmailViewModel` (for an email change); it overrides the account, client and appointment DAO groups and `DatabaseStorage` with fakes (stubbing the flows the Home ViewModel observes on creation) because the client database's `WebWorkerSQLiteDriver` needs a browser `Worker`, which Node lacks.

- `:library:files:impl`'s `JsFileProvider` keeps files in memory for the page's lifetime (a `single`), so on the web the personal data export JSON cache does not survive a reload.
- Ktor's JS engine rejects proxies, so `:shared:common`'s BuildKonfig sets `PROXY_URL` empty for the `js` target (`targetConfigs`); a local `bookkme.proxyUrl` only affects the apps.
- `:shared:common`'s `BuildKonfig` picks the variant with `getCurrentVariant()`, which only recognises Android task names, so every client build passes `-Pbuildkonfig.flavor`: `devDebug` locally (commands above, `Client` run configuration) and in the PR build, `devRelease` for the `develop` export and manual publishes of a branch, `prodRelease` for `client-v*` tags and manual publishes of a tag (the `kobweb-export` action's `flavor` input). Without it, the default `buildkonfig.flavor=any` from `gradle.properties` leaves `BASE_URL` empty.
- The JS `authDataPlatformModule` binds `JsPassKeyManager`, which throws `UnsupportedOperationException` from every method until a WebAuthn implementation exists, so passkey use cases fail on the web: `SignIn` maps it to `PasskeyVerificationFailed`, `FinishSignUp` and settings' `CreateNewPasskey` to `AccountCreationFailed`, while `ConfirmSensitiveAction` (and so settings' `DeleteAccount`) lets the `UnsupportedOperationException` through. `SignInWithTelegram` doesn't need one. The backend accepts `https://bookkme.app` as a WebAuthn origin; a passkey on `app.bookkme.com` would need it added.
- The API (`BASE_URL`, `https://bookkme.app/api` in production) is on another origin, so the backend's CORS configuration must allow `https://app.bookkme.com`.

## SQLite on the web

Room on JS runs SQLite WASM in a module Web Worker at `/sqlite/sqlite-worker.js` (`SQLITE_WORKER_PATH` in `:database:client`'s `jsMain`; the client database file is `bookk_me_client.db`). The app serves it from `src/jsMain/resources/public/sqlite/`, and `copySqliteWasm` copies `sqlite3.js`/`sqlite3.wasm`/`sqlite3-opfs-async-proxy.js` there from the `@sqlite.org/sqlite-wasm` npm package. The worker stores the database in OPFS. It turns off sqlite-wasm's `opfs-wl` VFS (`globalThis.sqlite3ApiConfig.disable.vfs`), which it never opens: every OPFS VFS starts its own `sqlite3-opfs-async-proxy.js` worker while SQLite loads, and sqlite-wasm waits up to 4 s for each before giving up on it, so an unused one only adds to a slow start. It uses `OpfsDb` when the page is cross-origin isolated: the production nginx sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, and the Telegram SDK is loaded with `crossorigin="anonymous"` so that it passes (telegram.org answers with `Access-Control-Allow-Origin: *` but no `Cross-Origin-Resource-Policy`). Any other cross-origin resource the app adds must be loaded the same way or send a `Cross-Origin-Resource-Policy` header. `OpfsDb` locks the file per operation, so every tab opens the same database (sqlite-wasm sets a 10 s `busy_timeout` on it); it is a different file from the SAH pool's, so a device that switches storage starts with an empty cache once. Telegram Web frames the Mini App and is not isolated itself, so there the app stays on the SAH pool. The worker logs the storage it picked to the console. Tabs sharing the file see each other's writes: after a committed transaction that changed rows the worker posts `changed` on the `bookkme-db-changes` `BroadcastChannel` (a transaction that changed nothing, such as Room's own invalidation refresh, is not announced, or the tab would keep re-checking after hearing itself), and every tab's `CrossTabInvalidation` makes Room re-query its observed flows when SQLite's `data_version` shows another connection committed (see `docs/database/README.md`). Otherwise it uses the `opfs-sahpool` VFS, which only one tab can hold, so any further tab (or a Mini App reopened while the previous one still holds it) falls back to an in-memory database. `DatabaseStorage` (`:database:schema`, bound by each database module) detects that from SQLite's empty main database file name, and `InitialAppDataFetch.timestampProtectedFetch` then fetches on every start instead of every 30 minutes, so the profile and other cached data are reloaded into the empty database. A persistent database that starts empty (switching storage, or a renamed SAH pool) is caught by the profile instead: a signed-in user without a local profile is always due for a fetch.

## Telegram Mini App

- `library/telegram/` (`:library:telegram`, package `library.telegram`, JS only) is the Telegram Mini App SDK: the `TelegramWebApp` external bindings, `TelegramSdk` (script loading and launch detection), `TelegramSession` (colour mode and language), and the `rememberTelegramLaunch()`/`TelegramHost` composables that follow Telegram's theme, paint its header, background and bottom bar and call `ready()`/`expand()`. It also binds the shared states to Telegram's native controls, which screens inside the Mini App use instead of the in-page components: `TelegramMainButton`/`TelegramSecondaryButton(webApp, ButtonState)` drive the native bottom buttons (text, visibility, enabled state, progress spinner, click) in the `ButtonActive`/`OnAction` colours (`ButtonInactive`/`ActionTextDisabled` while disabled or loading); `TelegramAppTopBar(webApp, AppBarState)` renders `AppTopBar` without its arrow and moves `onBackClick` to Telegram's `BackButton` (`TelegramBackButton` binds it alone); `TelegramSettingsButton(webApp, onClick)` shows the Settings item of Telegram's ⋯ menu (its `SettingsButton`) while it is composed and calls `onClick` when it is pressed; `ObserveTelegramNotifications(webApp, PresentationNotificationState)` is the Mini App's notification renderer: `Message` and `GlobalMessage` open a native `showPopup` (at most 3 buttons, `NEGATIVE` as `destructive`, the rest `default` with our own texts; a message without buttons, and every `GlobalMessage`, gets Telegram's `close` button; title/message/button texts are cut to Telegram's 64/256/64 limits, since the SDK throws past them), `SuccessHaptic` plays `HapticFeedback.notificationOccurred("success")`, an `InputMessage` (Telegram has no input popup) is cancelled through its `onCancel`, and the rest is dropped. Features newer than the client's Bot API version are gated by `TelegramWebApp.supports(TelegramFeature)`: below 7.10 the secondary button falls back to an in-page `TextButton` and the bottom bar keeps Telegram's colour, below 6.1 `TelegramAppTopBar` keeps the in-page arrow, below 6.2 popups are skipped, and below 7.0 `TelegramSettingsButton` does nothing (the Settings screen stays reachable through Home's gear). Any feature's `jsMain` that renders inside the Mini App depends on it.
- The Mini App's language is the Telegram user's `language_code`, falling back to the browser languages. Telegram's `telegram-web-app.js` is injected only when the URL hash carries `tgWebAppData`, so ordinary visitors never request telegram.org and see a short "this page opens in Telegram" note linking the site's `/clients` page instead. Kobweb rebuilds the URL from the *decoded* fragment whenever a route interceptor is registered, which splits `tgWebAppData` apart, so `initTelegramSdk` (`@InitKobweb` in `TelegramMiniApp.kt`, since Kobweb only collects init hooks from the app module; it runs before the first routing) captures the raw hash and `TelegramSdk` writes it back before loading the script. `TelegramHost` follows Telegram's `colorScheme` and `themeChanged` with the design system's palette and paints Telegram's header and background with `ColorToken.Background`.
- Inside Telegram, `TelegramMiniApp` shows `ClientBootstrapDestination` with `TelegramSignInDestination` as its `loginContent`; the app passes it two frames that both draw the logo: `TelegramMessageLayout` (a centred column, for the signing-in and failure messages) and `TelegramFormLayout` (a top-aligned, start-aligned column, for the consent form) and `TelegramMainContent(webApp)` as its `mainContent`. Both live in authorization presentation's `jsMain` with their `Web*State`s and `WebClientStateFactory` (bound in `AuthDi.js.kt`, implementing `ClientStateFactory`, the client app's counterpart of `AuthStateFactory`). `ClientBootstrapDestination` is the entry for every client surface, Telegram and the browser alike, each passing its own login and main content. Like the mobile bootstrap, `ClientBootstrapViewModel` observes `IsUserLoggedIn.asFlow()` and runs the throttled initial data fetch: a signed-in user goes straight to `mainContent` (the Home screen), and only a signed-out one sees `loginContent`; the screen switches to the main content by itself once sign-in stores the session, and back if the session ends. As on mobile, the session ends when a request comes back unauthorized: `ErrorMapperImpl` maps it to `PresentationNotification.Unauthorized`, `ObserveTelegramNotifications` hands it to `LocalUnauthorizedHandler` (`core:presentation` `jsMain`; `UnauthorizedHandler` itself is in `commonMain`), and `ClientBootstrapDestination` provides that as `ClientBootstrapViewModel.logOut()`, which runs `LogOut`; back on `loginContent`, Telegram signs the user in again silently from `initData`. The sign-in screen creates `TelegramSignInViewModel` with `parametersOf(webApp.initData)` and renders its phases. A returning Telegram user is signed in silently; the server answers a new one with `LEGAL_DOCUMENTS_NOT_ACCEPTED`, and only then does the page show the consent form: a welcome heading, the privacy policy and terms as rows of one card (each opening the document) with the consent checkbox below them, and "Create account". The button stays enabled; tapping it without the checkbox shows the acceptance error under the checkbox instead of signing in, which (like "Try again" after a failure) is Telegram's native main button through `TelegramMainButton`. The links open through `Telegram.WebApp.openLink`, so the Mini App never navigates away.
- New client screens (booking, settings) go in their feature's `jsMain`, depend on `:library:telegram` and use its native controls; the app only hosts them. Each screen is split the way Android splits `FooDestination.kt` and `FooScreen.kt`: `FooDestination.kt` holds the public `@Composable fun FooDestination(...)` the app calls, which takes the screen arguments and the feature's navigation object, gets the ViewModel with `rememberViewModel`, and observes `ObserveTelegramNotifications` and `ObserveNavigation`, whose `when` maps each of the screen's `FooDestinations` to a call on that object (`Back -> navigation.onBack()`), as Android's `FooDestination.kt` does; `FooScreen.kt` holds `@Composable internal fun FooScreen(state: FooState, ...)`, which only renders state (Telegram's `TelegramAppTopBar`/`TelegramMainButton` included, the counterparts of `AppTopBar` and the screen's button) and never touches Koin or the ViewModel. Feature modules are not Kobweb libraries, so Kobweb never registers a `CssStyle` declared in them and its `toModifier()` throws on first composition: use the `:designsystem` styles and a plain `Modifier` for screen layout, and move a style that needs breakpoints or colour mode into `:designsystem`'s `jsMain`.
- **Home** (`ClientHomeDestination`/`ClientHomeScreen`, dashboard presentation `jsMain`, `ClientHomeViewModel` in `commonMain`, state from `ClientDashboardStateFactory`/`WebClientDashboardStateFactory`): the client's dashboard, a greeting with the first name from `UserProfileCRUD.observe()` and a Settings button, the client's upcoming bookings (`GetUpcomingBookings`, confirmed appointments and requests waiting for confirmation, with `ColorToken` status pills) and "Book again" (`GetSavedBusinesses`), both named through `GetBusinesses` (one `POST /api/business/bulk`, saved into `business`), all rendered from the client database and refreshed when the screen opens; while both lists load empty it shows the "Nothing to book yet" steps instead. Errors stay inline as banners with a retry text button, so the screen has no in-page primary button; popups go through `ObserveTelegramNotifications`. A launch with a start parameter (`initDataUnsafe.start_param`, from a `t.me/<bot>/<app>?startapp=<value>` link) opens a business: a dashed business id is used as is, anything else is a business link name resolved through business's `ResolveBusinessLink` (`GET /api/business/link/{name}`, the name the owner sets in the business app). The business is then saved (`SaveBusiness`) and `ClientHomeDestinations.Services` pushed; a name no business uses shows a popup and the Home screen loads as usual. The business app shares the link on BuildKonfig `CLIENT_APP_URL` (`https://app.bookkme.com`, dev `https://local-app.bookkme.app`), bound as `ClientAppUrl`. Services opens the services step, an upcoming booking opens the request or the appointment details (by its status) and the Settings button opens Settings; All bookings is pushed as a destination but not handled yet (#187).
- **Navigation**: `TelegramMainContent` (`telegram/`) keeps the Mini App's screens on a `BackStack<ClientScreen>` (`navigation/ClientScreen`, `core:presentation`'s `jsMain` `navigation/BackStack`) rendered by `:designsystem`'s `BackStackHost`, which slides screens in and out like the native apps (see `apps/site/README.md`): outside a transition only the top screen is composed, but each entry keeps its ViewModels in its own `ViewModelStore`, so going back to Home finds the same `ClientHomeViewModel` (its launch business is not opened twice) and a popped screen's ViewModel is cleared once it has slid away. Native Telegram controls attach only for the current screen (`LocalIsCurrentScreen`). The URL never changes, so the `tgWebAppData` hash stays untouched. As on Android, each feature declares a navigation class of lambdas in its `jsMain` `navigation/` package (`BookingNavigation`, dashboard's `ClientHomeNavigation`, the counterparts of `ServicesNavigation`), its destinations decide which lambda each ViewModel destination calls, and the app builds the objects over the stack in `navigation/Remember<Feature>Navigation.kt` (like `rememberServicesNavigation(controller)`; settings' `SettingsNavigation` also opens the site's pages through `webApp.openLink` with `ClientLink.sitePage`): those are the only places that `push`/`pop`, and a destination not built yet gets an empty lambda. `TelegramMainContent` only maps each `ClientScreen` to its destination. A screen's `Back` destination comes from Telegram's native `BackButton` (`TelegramAppTopBar`).
- **Services** (`BookingServicesDestination`/`BookingServicesScreen`, `feature/booking/presentation` `jsMain`, `BookingServicesViewModel` in `commonMain`, state from `BookingStateFactory`/`WebBookingStateFactory`): the first booking step. The booking feature holds the client booking flow (services, specialist, time, confirmation); its presentation uses only booking's own use cases, which wrap the business and services ones, and its strings are `BookingRes` (`booking_` keys). The business name as a small secondary label over the bold "Pick your services." title, then its available services grouped by service group, one `OptionsQuantityList` per group sharing one `OptionsMultiPickerState`, each service on its own card with its duration and price (`Money` formatted by `Intl` in the browser's locale) and an "Add" button that turns into a − count + stepper. The name and services come from booking's `GetBookingCatalog` (wrapping `GetBusinesses` and `GetBusinessServices`; unavailable services left out, groups in creation order), rendered from the client database and refreshed in parallel when the screen opens; a failed refresh shows the error inline (full-screen with retry when nothing is cached, a retry banner over cached services). While something is picked, a `BookingTotalBar` (booking's `RevealingBottomBar`, shared with the Specialist step) slides up and sticks to the bottom of the page above Telegram's `MainButton` (and slides away when the last pick is removed) with the state's `BookingTotal`, computed in the ViewModel by `bookingTotal()`: the number of picked services (a `booking_services_count` plural, counting each repeat) and their total duration, and the total price. The `MainButton` always reads "Continue" and is disabled (with no bar) while nothing is picked; pressing it saves the picks with `SetBookingServices` into booking's in-memory booking preparation (one per business) and then pushes `BookingServicesDestinations.Specialist(businessId)` (the Specialist step), which reads them from there. The steppers change only the screen's own selection, so picks are not approved until Continue; when the screen opens it restores the last approved services from the first `GetBookingPreparation.flow` value, and later values never overwrite the client's unsaved picks. The approved services last until the page reloads or the user logs out.
- **Specialist** (`BookingSpecialistDestination`/`BookingSpecialistScreen`, `BookingSpecialistViewModel`, state from the same factories): the second step, "Who would you like?", under the business name as a small secondary label (from `GetBookingCatalog.flow`), laid out like the Services step. A `CardGrid` lists the employees clients can book at the business who provide every approved service (booking's `GetBookingSpecialists`, wrapping employees' `GetBookableEmployees`: `GET /api/business/{businessId}/employee/bookable`), each on a `SelectableCardButton` with a large `InitialsAvatar` over the full name, bold and centred in one line of text, and an empty state when nobody does. The employees are cached in `ClientDatabase` (employees' `bookable_employee` tables; any signed-in user may read that endpoint), so coming back to the step, or reopening the app, shows them at once while they refresh; a failed load shows the error inline with retry. Exactly one person is selected (outlined in `ActionText`): the one the client tapped, else the approved specialist from the booking preparation if still listed, else the first in the list. Tapping a card only selects it. The same `BookingTotalBar` as on Services (the shared `BookingTotal`: the approved services' count, total duration and total price, from `GetBookingPreparation.flow`) sits above Telegram's `MainButton`, which reads "Continue with {first name}" (`booking_specialist_continue`) and is disabled, reading "Continue", while nobody is listed. Pressing it saves the selected person with `SetBookingSpecialist` into the booking preparation (approving services again on the previous step forgets them; picking another person forgets the time picked for the previous one) and pushes `BookingSpecialistDestinations.DateTime(businessId)`, the Date & time step.
- **Date & time** (`BookingDateTimeDestination`/`BookingDateTimeScreen`, `BookingDateTimeViewModel`, state from the same factories): the third step. Over the two-tone "Choose a time. These are all free." title, the business name and the picked specialist's full name sit side by side as small secondary labels split by a `VerticalDivider` (booking's `GetBookingTimetable.flow`, from the cached business and bookable employees). Under it the month of the selected date and a "Pick another date" `TextButton` that opens the browser's native date picker (`:designsystem`'s `NativeDatePicker` over the shared `DatePickerState`, no earlier than today in the business's time zone); the picked date becomes the selected day and the week strip below shows its week. The strip is seven `SelectableCardButton` tiles from the locale's first day of week (`startOfWeek()`, `Intl.Locale.getWeekInfo`), each with the short weekday ("Today" for today) over the day number; days before today are disabled, days with no free time are struck through and disabled, the selected day is outlined. The free times of the selected day come from the backend only (booking's `GetBookingSlots` → appointments' `GetFreeSlots`, `POST /api/appointments/slots`, backend #192, one request per shown week, never cached), shown as a four-column grid of time chips grouped into Morning (before 12:00), Afternoon (before 17:00) and Evening, in the business's time zone. A day with none says the business is closed on it (its cached schedule has the weekday off or a day off) or that it has no free times; a business without appointments says it takes no online bookings; any other failure shows inline with Retry. Until the client picks a date, the step opens on the approved time's day, else today, and moves to the week's first day with free times when that day has none. The `BookingTotalBar` shows the services' total until a time is picked, then the picked day and time ("Tue, 24 Nov · 14:30") beside the price. Telegram's `MainButton` reads "Pick a time" and is disabled until a time is picked, then "Continue": it saves the time's start with `SetBookingSlot` into the booking preparation and pushes `BookingDateTimeDestinations.Review(businessId)`, the Review step. Coming back restores the approved time while it is still free.
- **Review** (`BookingReviewDestination`/`BookingReviewScreen`, `BookingReviewViewModel`, state from the same factories): the last step: the business name as a small secondary label over the bold "Almost there." title (the design's secondary "Check your request." is not built). An `AppCard` sums the request up from `GetBookingTimetable.flow` and `GetBookingPreparation.flow`: the picked day ("Tue, 24 Nov") over "14:30–15:35 · Specialist" (the business name is already above the title) (the end is the start plus the services' total duration, in the business's time zone), one row per approved service with its price (a repeated one as "Beard trim × 2" with the summed price; a service whose cached price changed since it was approved shows the approved price struck through in grey beside the new one in bold, and sending approves the new price) and the total. When the business wrote a note to clients (its "Note to clients" in the business app), an `InfoNote` under "From <business>" shows it below the card: booking's `GetBusinessMessage` reads it from `ClientDatabase`'s `booking_info` (appointments' `GetBookingInfo`) and refreshes it from `GET /api/appointments/booking-info/{businessId}` when the step opens; a 404 (the business no longer takes appointments) says the business takes no online bookings and leaves the booking flow, any other failed refresh is only logged and keeps the cached note. Below it an optional "Note for the business" `TextField` (three lines tall, 2048 characters at most) and the notice that the business confirms the request and the answer arrives as a message here. Telegram's `MainButton` "Send request" shows its progress while booking's `SendBookingRequest` sends exactly what the summary shows: it asks services' `CreateQuote` for a fresh quote (each service once per unit), refuses it unless every service is still available at the shown price and duration, and sends appointments' `CreateAppointmentRequest` with its token; on success it plays the success haptic, clears the business's booking preparation (an emptied preparation never blanks the shown request), refreshes the upcoming bookings so Home lists the new pending request (a failed refresh is dropped) and pushes `BookingReviewDestinations.Sent` with the `SentBookingRequest` it returns, the Request sent step. The known failures each open one native popup: the time was taken or no longer fits the schedule (`EMPLOYEE_BUSY` and the schedule and past-date codes), too many requests waiting at the business, the prices changed (a quote at other prices than the summary, or the backend's `PriceChanged`: the client checks the new prices in place and sends again, no going back), the services changed since they were picked (a picked service no longer offered, or a quote whose services or durations differ from the summary); on a price or service change `SendBookingRequest` first refreshes the business's services silently, so the summary shows the current prices, and a specialist who can no longer be booked; anything else goes through the error mapper.
- **Request sent** (`BookingSentDestination`/`BookingSentScreen`, `BookingSentViewModel`, state from the same factories): the confirmation after the request is sent. `ClientScreen.Sent` replaces every screen above Home (`BackStack.replaceAboveRoot`), so it slides in from the Review step but Telegram's `BackButton` returns to Home, not to Review, as does the `MainButton` "Done". It shows `:designsystem`'s `SuccessMark` (the outlined Material check on a 16% `Success` tint), the bold "Request sent." title (the design's secondary "Now it's <business>'s move." is not built) and that a message arrives in this chat once the business confirms. Below it a `CardButton` sums up the sent request: a `StatusPill` ("Waiting for confirmation" in `SecondaryText`, "Confirmed" in `Success` once the business confirms), the day ("Tue, 24 Nov") and "14:30–15:35 · Haircut, Beard trim × 2". It comes from booking's `GetSentBooking.flow`, which finds the request `SendBookingRequest` returned (business, specialist and start; the backend answers with no body, so there is no id) among the upcoming bookings it refreshed into the client database, in the device's time zone like Home; the card is left out while the request is not cached (that refresh failed). Tapping it opens the request details while the request waits, the appointment details once it is confirmed. The "Book something else" `TextButton` replaces the step with the same business's Services step, which starts empty because sending cleared the booking preparation.
- **Booking details** (`BookingRequestDetailsDestination` and `BookingAppointmentDetailsDestination`, both hosting the stateless `BookingDetailsScreen` through `BookingDetailsHost`; `BookingRequestDetailsViewModel` and `BookingAppointmentDetailsViewModel` filling one `BookingDetailsState` from the same factories, formatted by the shared `BookingDetailsItems`): one booking request or one appointment, two routes because they are different backend records with their own ids, statuses and actions. Home and Request sent push `ClientScreen.BookingRequestDetails(requestId)` for a waiting booking and `ClientScreen.BookingAppointmentDetails(appointmentId)` for a confirmed one. Each reads its own cached row by id whatever its status (booking's `GetBookingRequestDetails`/`GetBookingAppointmentDetails` → appointments' `GetClientAppointmentRequest`/`GetClientAppointment`), so any list that caches the client's bookings can open them; there is no refresh, since no client route reads one booking, and the screen goes back when its row disappears (an upcoming refresh deletes a request the business answered meanwhile). A `StatusPill` over the business name as the bold title (the design's two-tone "Fri, 27 Nov. 11:00 at Nail Room." title is not built), then an `AppCard` with When ("Fri 27 Nov, 11:00–12:00"), With (the specialist) and Your note (the request's note or the appointment's `clientNote`, left out when blank) rows, one row per booked service with its price (a repeated one as "Gel polish × 2" with the summed price; for an appointment the services and price the business charged after a price adjustment) and the total, and below it a small secondary explanation of the status. Request statuses: Waiting for confirmation, Confirmed, Declined (`Error`) and Closed (withdrawn or not answered in time, which the backend does not tell apart); appointment statuses: Confirmed (`Success`), Done (also unresolved past visits), Cancelled and Missed (`Error`). Only a waiting request has Telegram's `MainButton`: "Withdraw request" in the destructive style (`TelegramButtonStyle.DESTRUCTIVE`: `Error` text on the `Elevated` card colour); it opens a native popup "Withdraw request?" with Keep and a destructive Withdraw, which calls booking's `WithdrawBookingRequest` (appointments' `WithdrawAppointmentRequest`, `POST /api/appointments/request/{id}/withdraw`, setting the cached request to `CANCELLED`, so the screen shows it Closed while it leaves) with the button's progress, plays the success haptic and pushes `BookingDetailsDestinations.Bookings`, which pops back until My bookings (#187) exists. A request the business answered meanwhile opens one popup (already confirmed, or no longer waiting) after the upcoming bookings were refreshed, and goes back; anything else goes through the error mapper and stays.

- **Settings** (`SettingsDestination`/`SettingsScreen`, settings presentation `jsMain`, the mobile apps' `SettingsDashboardViewModel` in `commonMain`, state from `SettingsStateFactory`/`WebSettingsStateFactory`): opened by Home's gear and by the Settings item of Telegram's ⋯ menu (`TelegramSettingsButton` in `TelegramMainContent`, Bot API 7.0+; it does nothing while Settings is already the current screen). The same settings as the apps minus what Telegram owns: no appearance (the Mini App follows Telegram's theme), passkey, log out, push notifications or crash reports. The shared state still carries those parts for the apps; the web screen just does not render them. On top a profile header: the initials in an `InitialsAvatar` (`EXTRA_LARGE`), the full name (`ProfileSection.fullName`/`initials`, computed by the ViewModel from `GetSettings`, loaded when the screen is presented through `SendLifecycleEventsTo`), "Businesses see this name when you book" and the "Edit booking profile" `TextButton` (`ProfileSection.edit`). Below it three `MenuCard`s (`:designsystem`): Notifications, Privacy (with the red "Action required" `StatusText` while a legal document awaits confirmation, from `GetLegalDocumentStatuses`, refreshed when presented) and Export my data; Contact us, Terms of Use and Privacy Policy, which open the site's `/contact`, `/terms` and `/privacy` pages in the user's language through Telegram's `openLink` (a Mini App cannot open `mailto:`, so the web shows the Contact page, which lists the support address, where the apps write an email); and the destructive Delete account row. Every row is a `ButtonState` whose `onClick` the ViewModel sets to push a `SettingsDashboardDestination`; `SettingsDestination` maps them onto `SettingsNavigation`, which `rememberSettingsNavigation` builds: Edit booking profile pushes `ClientScreen.BookingProfile`, the account rows push `NotificationSettings`, `PrivacySettings`, `PersonalDataExport` and `DeleteAccount`. Back is Telegram's `BackButton`, bound to `SettingsNavigation.onBack` directly, because the apps show Settings as a root tab whose app bar has no back action.
- **Booking profile** (`BookingProfileDestination`/`BookingProfileScreen`, settings presentation `jsMain`, the mobile apps' `EditProfileViewModel` in `commonMain`, state from `SettingsStateFactory`/`WebSettingsStateFactory`): the name and email businesses see when the client books, opened by Settings' "Edit booking profile". The bold "Booking profile." title (`settings_booking_profile_title`; the apps title the same screen "Edit profile" in their app bar, so the web renders its own heading and binds only `appBar.onBackClick` to Telegram's `BackButton`), one Full name `TextField` (the apps show the same single field) and the email in an `ActionField` with "Change" and the hint that a new email is confirmed with a code sent to it. The name loads once when the screen is first presented (`GetSettings`, from the cached profile, first and last name joined by a space); the email is read again every time it is presented, so it shows the new address after an email change. Telegram's `MainButton` "Save" is enabled once the name differs from the saved one; pressing it splits the name on whitespace (`FullName.parse`: the first word is the first name, the remaining words joined by one space the last name, which may be empty), checks the first name is at least 2 characters (`ValidateName`) and shows an error under the field only, otherwise saves both with `EditProfile` (`PATCH /api/user/me`, keeping the stored email; the backend stores an empty last name as sent) with the button's progress, plays the success haptic and goes back; a failure goes through the error mapper as a native popup. The design's Phone field is not built: neither app edits the phone. "Change" pushes `ClientScreen.ChangeEmail` through `SettingsNavigation.toChangeEmail`.
- **Change email** (`ChangeEmailDestination`/`ChangeEmailScreen`, authorization presentation `jsMain`, the apps' `ChangeEmailViewModel`) and **Verify email** (`VerifyEmailChangeDestination`/`VerifyEmailScreen`, the apps' `VerifyEmailViewModel` with `VerifyEmailRequest.EmailChange`), both drawn by `EmailChangeLayout` (the state's app-bar title as the bold heading over its explanation) with Telegram's `BackButton` and `MainButton`: the first asks for the new address ("Send code", `StartEmailChange`: `POST /api/auth/email`, errors under the field) and pushes `ClientScreen.VerifyEmail(pendingEmailChange)`; the second takes the 6-digit code (sent automatically once complete, or with "Verify"), offers "Send a new code" after its countdown and confirms with `ConfirmEmailChange` (`POST /api/auth/email/confirm`, which writes the new address into the cached profile), then plays the success haptic, opens a native popup that the email changed and pops back to the booking profile (`BackStack.popTo(ClientScreen.BookingProfile)`). The client app's `EmailChangeNavigation` (authorization `jsMain` `navigation/`, built by `rememberEmailChangeNavigation`) maps their destinations. Both ViewModels take `EmailVerificationStateFactory`, which `AuthStateFactory` extends on the apps, so the web implements only these two states.

## Releases and deployment

The app has its own release line, mirroring the site's: `client-dev-merge-assemble.yml` exports `develop` with `devRelease`, `client-main-tag.yml` ("Client Release") runs on `client-vX.Y.Z` tags with `prodRelease` and publishes `ghcr.io/nocturneproperties/bookkme-webapp:<X.Y.Z>` (not `bookkme-client`, which would read as the image of this whole `bookkme-client` repository), and `client-branch-manual.yml` publishes a branch or tag on demand. The shared `kobweb-export` and `kobweb-image` actions take the app name; `kobweb-image` also takes the image name (`bookkme-site`, `bookkme-webapp`). PRs run `:client:jsNodeTest` and `:client:jsBrowserProductionWebpack` in `android-pr-build.yml`. "Mark Released" moves issues labeled `client` on `client-v*` releases; client issues use the `bug-client`/`feature-client` templates.

The image runs Kobweb's own server in the FULLSTACK layout on port 8081 (`.kobweb/conf.yaml`). It is deployed by hand behind nginx on `app.bookkme.com`, which must allow framing by Telegram Web (`frame-ancestors https://web.telegram.org`), unlike the site.
