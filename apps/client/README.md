# Bookk client web app (`apps/client/`)

`:client` is the Kobweb (Kotlin/JS, Compose HTML + Silk) app for people who book, served on its own host, `https://app.bookkme.com`. Today it is the Telegram Mini App; browser booking will join it later. It is separate from the marketing site (`:site`, `bookkme.com`) so the site's download stays free of the client stack (Koin, Ktor, Room/SQLite WASM, sign-in, the Telegram SDK) and each host can send its own headers: the Mini App must be frameable by Telegram Web, the site need not be.

Read [`apps/site/README.md`](../site/README.md) first: the web design system (`:site:designsystem`), the JS-runtime rules, the DOM API setup and the language model apply here too. The project-wide rules in the root `AGENTS.md` apply as everywhere.

## Commands

- **Run the client app**: `./gradlew :client:kobwebStart -t -Pbuildkonfig.flavor=devDebug` (http://localhost:8081, so it runs next to the site on 8080; the `Client` run configuration passes the same flavor), stop with `./gradlew :client:kobwebStop`.
- **Run JS tests**: `./gradlew :client:jsNodeTest -Pbuildkonfig.flavor=devDebug`.
- **Export as CI does**: `./gradlew :client:kobwebExport -PkobwebBuildTarget=RELEASE -PkobwebExportLayout=FULLSTACK -Pbuildkonfig.flavor=devRelease`.

## Layout

Code in `src/jsMain/kotlin/me/bookk/client/`, copy in `src/commonMain/moko-resources` (`ClientRes`, keys prefixed `client_`; EN with `uk/` and `pl/` like the site, no `ru/`), static files in `src/jsMain/resources/public/`:

- `AppEntry.kt`: the `@App` (Silk, colour mode, `LocalizedContent` with the `ClientRes` and `AuthRes` strings). Keep authorization string keys unique against `client_`, `DesignSystem` and `CorePresentation` keys, since the merged provider resolves by key alone.
- `pages/`: thin Kobweb `@Page` files. `Index.kt` (`/`) is the Telegram Mini App entry, the URL to register as the bot's Mini App (BotFather) and Menu Button: `https://app.bookkme.com/`. Its `@InitRoute` shows the preferred language (Kobweb's default while exporting) and starts Koin.
- `layout/ClientPageHead`: title (`<page> · BookkMe`), description and `robots: noindex` through `:site:designsystem`'s `HeadTags`. The app has no canonical, hreflang or Open Graph tags, no sitemap and no language URL prefixes; `public/robots.txt` disallows everything.
- `navigation/ClientLink`: links out of the app. `ClientLink.siteClients(...)` points at the site's `/clients` page in the current language, on the `SiteUrl` from Koin (BuildKonfig `SITE_URL`, so dev builds link the dev site).
- `telegram/`: `TelegramMiniApp` and `TelegramMessage` (see **Telegram Mini App**).
- `di/ClientApp.kt`: `initClientApp()` (see **Koin**).
- Logos and favicons come from `:site:designsystem`'s `public/` (shared with the site); the app adds no manifest or share image because it is not meant to be installed or linked from search.

## Koin

`initClientApp()` is the web counterpart of `:shared`'s `initBusinessApp`, called from the `@InitRoute` of each page that uses the API (currently `/`). It returns early once Koin is running, so revisiting a page in the same session keeps the existing graph. It installs `:shared:common`'s `initLogging()` and `commonModule()` (the same Ktor client as the apps on the JS engine: protobuf, bearer auth with refresh, `X-Platform`/`Accept-Language` headers; plus `ErrorMapper` and `SiteUrl`), and the web modules that client and Telegram sign-in need: `deviceModule()`, `cacheModule()`, `filesModule()`, `clientDatabaseModule()`, `authDomainModule()`, `authDataModule()`, `settingsDomainModule()`, `settingsDataModule()` (settings provides the legal documents `InitialAppDataFetch` preloads, and its `AppStartAction`, `BackgroundDataFetchAction` and `LogOutAction` bindings join the web fetch and logout) and `authPresentationModule()`.

Add a web feature's domain and data modules there when the app starts using it, together with whatever its trigger and `LogOutAction` bindings need: `getAll()` builds every bound action, so one unresolvable dependency breaks `InitialAppDataFetch` or `LogOut` for the whole app. `ClientAppTest` checks the graph resolves, including `SignInWithTelegram` and `LogOut`; it overrides the account DAOs with mocks because the client database's `WebWorkerSQLiteDriver` needs a browser `Worker`, which Node lacks.

- `:library:files:impl`'s `JsFileProvider` keeps files in memory for the page's lifetime (a `single`), so on the web the personal data export JSON cache does not survive a reload.
- Ktor's JS engine rejects proxies, so `:shared:common`'s BuildKonfig sets `PROXY_URL` empty for the `js` target (`targetConfigs`); a local `bookk.proxyUrl` only affects the apps.
- `:shared:common`'s `BuildKonfig` picks the variant with `getCurrentVariant()`, which only recognises Android task names, so every client build passes `-Pbuildkonfig.flavor`: `devDebug` locally (commands above, `Client` run configuration) and in the PR build, `devRelease` for the `develop` export and manual publishes of a branch, `prodRelease` for `client-v*` tags and manual publishes of a tag (the `kobweb-export` action's `flavor` input). Without it, the default `buildkonfig.flavor=any` from `gradle.properties` leaves `BASE_URL` empty.
- The JS `authDataPlatformModule` binds `JsPassKeyManager`, which throws `UnsupportedOperationException` from every method until a WebAuthn implementation exists, so passkey use cases fail on the web: `SignIn` maps it to `PasskeyVerificationFailed`, `FinishSignUp` and settings' `CreateNewPasskey` to `AccountCreationFailed`, while `ConfirmSensitiveAction` (and so settings' `DeleteAccount`) lets the `UnsupportedOperationException` through. `SignInWithTelegram` doesn't need one. The backend accepts `https://bookkme.app` as a WebAuthn origin; a passkey on `app.bookkme.com` would need it added.
- The API (`BASE_URL`, `https://bookkme.app/api` in production) is on another origin, so the backend's CORS configuration must allow `https://app.bookkme.com`.

## SQLite on the web

Room on JS runs SQLite WASM in a module Web Worker at `/sqlite/sqlite-worker.js` (`SQLITE_WORKER_PATH` in `:database:client`'s `jsMain`; the client database file is `bookk_me_client.db`). The app serves it from `src/jsMain/resources/public/sqlite/`, and `copySqliteWasm` copies `sqlite3.js`/`sqlite3.wasm`/`sqlite3-opfs-async-proxy.js` there from the `@sqlite.org/sqlite-wasm` npm package. The worker stores the database in OPFS. It uses `OpfsDb` when the page is cross-origin isolated (COOP/COEP headers). Otherwise it uses the `opfs-sahpool` VFS, which only one tab can hold, so any further tab falls back to an in-memory database.

## Telegram Mini App

- `library/telegram/` (`:library:telegram`, package `library.telegram`, JS only) is the Telegram Mini App SDK: the `TelegramWebApp` external bindings, `TelegramSdk` (script loading and launch detection), `TelegramSession` (colour mode and language), and the `rememberTelegramLaunch()`/`TelegramHost` composables that follow Telegram's theme, paint its header, background and bottom bar and call `ready()`/`expand()`. It also binds the shared states to Telegram's native controls, which screens inside the Mini App use instead of the in-page components: `TelegramMainButton`/`TelegramSecondaryButton(webApp, ButtonState)` drive the native bottom buttons (text, visibility, enabled state, progress spinner, click) in the `ButtonActive`/`OnAction` colours (`ButtonInactive`/`ActionTextDisabled` while disabled or loading); `TelegramAppTopBar(webApp, AppBarState)` renders `AppTopBar` without its arrow and moves `onBackClick` to Telegram's `BackButton` (`TelegramBackButton` binds it alone); `ObserveTelegramNotifications(webApp, PresentationNotificationState)` is the Mini App's notification renderer: `Message` and `GlobalMessage` open a native `showPopup` (at most 3 buttons, `NEGATIVE` as `destructive`, the rest `default` with our own texts; a message without buttons, and every `GlobalMessage`, gets Telegram's `close` button; title/message/button texts are cut to Telegram's 64/256/64 limits, since the SDK throws past them), `SuccessHaptic` plays `HapticFeedback.notificationOccurred("success")`, an `InputMessage` (Telegram has no input popup) is cancelled through its `onCancel`, and the rest is dropped. Features newer than the client's Bot API version are gated by `TelegramWebApp.supports(TelegramFeature)`: below 7.10 the secondary button falls back to an in-page `TextButton` and the bottom bar keeps Telegram's colour, below 6.1 `TelegramAppTopBar` keeps the in-page arrow, and below 6.2 popups are skipped. Any feature's `jsMain` that renders inside the Mini App depends on it.
- The Mini App's language is the Telegram user's `language_code`, falling back to the browser languages. Telegram's `telegram-web-app.js` is injected only when the URL hash carries `tgWebAppData`, so ordinary visitors never request telegram.org and see a short "this page opens in Telegram" note linking the site's `/clients` page instead. Kobweb rebuilds the URL from the *decoded* fragment whenever a route interceptor is registered, which splits `tgWebAppData` apart, so `initTelegramSdk` (`@InitKobweb` in `TelegramMiniApp.kt`, since Kobweb only collects init hooks from the app module; it runs before the first routing) captures the raw hash and `TelegramSdk` writes it back before loading the script. `TelegramHost` follows Telegram's `colorScheme` and `themeChanged` with the design system's palette and paints Telegram's header and background with `ColorToken.Background`.
- Inside Telegram, `TelegramMiniApp` wraps the screen in `TelegramMessageLayout` (logo and column) and shows `ClientBootstrapScreen` with `TelegramSignInScreen` as its `loginContent`. Both live in authorization presentation's `jsMain` with their `Web*State`s and `WebClientStateFactory` (bound in `AuthDi.js.kt`, implementing `ClientStateFactory`, the client app's counterpart of `AuthStateFactory`). `ClientBootstrapScreen` is the entry for every client surface, Telegram and the browser alike, each passing its own login and main content. Like the mobile bootstrap, `ClientBootstrapViewModel` observes `IsUserLoggedIn.asFlow()` and runs the throttled initial data fetch: a signed-in user goes straight to `mainContent` (currently the "booking is on its way" text, until client booking exists), and only a signed-out one sees `loginContent`; the screen switches to the main content by itself once sign-in stores the session, and back if the session ends. The sign-in screen creates `TelegramSignInViewModel` with `parametersOf(webApp.initData)` and renders its phases. A returning Telegram user is signed in silently; the server answers a new one with `LEGAL_DOCUMENTS_NOT_ACCEPTED`, and only then does the page show the privacy policy and terms links, the consent checkbox and "Create account", which (like "Try again" after a failure) is Telegram's native main button through `TelegramMainButton`. The links open through `Telegram.WebApp.openLink`, so the Mini App never navigates away.
- New client screens (booking, settings) go in their feature's `jsMain`, depend on `:library:telegram` and use its native controls; the app only hosts them.

## Releases and deployment

The app has its own release line, mirroring the site's: `client-dev-merge-assemble.yml` exports `develop` with `devRelease`, `client-main-tag.yml` ("Client Release") runs on `client-vX.Y.Z` tags with `prodRelease` and publishes `ghcr.io/nocturneproperties/bookkme-webapp:<X.Y.Z>` (not `bookkme-client`, which would read as the image of this whole `bookkme-client` repository), and `client-branch-manual.yml` publishes a branch or tag on demand. The shared `kobweb-export` and `kobweb-image` actions take the app name; `kobweb-image` also takes the image name (`bookkme-site`, `bookkme-webapp`). PRs run `:client:jsNodeTest` and `:client:jsBrowserProductionWebpack` in `android-pr-build.yml`. "Mark Released" moves issues labeled `client` on `client-v*` releases; client issues use the `bug-client`/`feature-client` templates.

The image runs Kobweb's own server in the FULLSTACK layout on port 8081 (`.kobweb/conf.yaml`). It is deployed by hand behind nginx on `app.bookkme.com`, which must allow framing by Telegram Web (`frame-ancestors https://web.telegram.org`), unlike the site.
