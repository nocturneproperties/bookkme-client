# Bookk website (`site/`)

Kobweb (Kotlin/JS, Compose HTML + Silk) website. The domain layer, `core:presentation` and the shared `designsystem` state interfaces also compile for JS; the web state implementations and components live in `:site:designsystem`.

This file holds the web-only guidelines. The project-wide rules in the root `AGENTS.md` (architecture, layer boundaries, no comments, block bodies, strings and translations, testing) apply here too, and its **Web target** section lists the JS-target rules shared with mobile work.

## Commands

- **Run the website**: `./gradlew :site:kobwebStart -t` (http://localhost:8080), stop with `./gradlew :site:kobwebStop`
- **Run JS tests**: `./gradlew jsNodeTest` (web-target modules' `commonTest` + `jsTest` on Node.js; one module: `./gradlew :<module>:jsNodeTest`)

## Layout

- `site/`: the `:site` application. Pages in `src/jsMain/kotlin/me/bookk/site/pages/`, static files in `src/jsMain/resources/public/`, copy in `src/commonMain/moko-resources`.
- `site/designsystem/`: the web design system (`:site:designsystem`).
- `site/domcompat/`: the DOM symbols `kotlinx-browser` lacks (`:site:domcompat`, see **DOM API** below).
- `site/legal/`: published legal texts (see [`legal/README.md`](legal/README.md)).

The JS-only site modules (`:site`, `:site:designsystem`, `:site:domcompat`) apply `convention.kmm.web` instead of the bare Kotlin Multiplatform plugin. It applies Kotlin Multiplatform with the shared compiler options (`applyCompilerOptions()` in `KotlinConvention.kt`, e.g. `-Xexpect-actual-classes`) but no Android/iOS targets or dependencies. Put compiler flags every module needs in `applyCompilerOptions()`, not in a module's build script.

## Shared code on the JS target

- Room on JS runs SQLite WASM in a module Web Worker at `/sqlite/sqlite-worker.js` (`SQLITE_WORKER_PATH` in `:database`'s `jsMain`). The site serves it from `site/src/jsMain/resources/public/sqlite/`, and `:site`'s `copySqliteWasm` task copies `sqlite3.js`/`sqlite3.wasm`/`sqlite3-opfs-async-proxy.js` there from the `@sqlite.org/sqlite-wasm` npm package. The worker stores the database in OPFS. It uses `OpfsDb` when the page is cross-origin isolated (COOP/COEP headers). Otherwise it uses the `opfs-sahpool` VFS, which only one tab can hold, so any further tab falls back to an in-memory database.
- DataStore on JS (`:library:cache:impl` `jsMain`) uses `WebLocalStorage` wrapped in `DataChangeStorage`. DataStore 1.3.0 bumps the version key before it writes the data and only listens for the version key, so other tabs re-read stale data. `DataChangeCoordinator` notifies on the data key's `storage` event instead, which keeps open tabs in sync live. Do not switch to `WebOpfsStorage`: in 1.3.0 a tab can read its own just-written value back stale.
- `jsMain` actuals are built on the browser's `Intl` APIs where the other platforms use ICU/Foundation (`JsDateLocalizer`, `JsTextCollator`, `startOfWeek`, `Currency`). `core:presentation`'s `ViewModel` is a commonMain class over `expect abstract class PlatformViewModel` (Android: androidx `ViewModel`; iOS/JS: its own scope and a public `onCleared()`). Test JS-only behavior in `jsTest`.
- JS formatting follows `StringDesc.localeType` (set by the site's language picker); with `LocaleType.System` it falls back to the browser default.
- kotlinx-datetime on JS only knows the system zone unless `@js-joda/timezone` is loaded; `:core`'s `jsMain` (`me.bookk.core.time.JsJodaTimeZone.kt`) does that for every consumer — do not remove it.
- JS tests run on Node via `jsNodeTest` (browser test tasks are disabled). moko's generated JS code loads string files with `require("./localization/*.json")`, which only webpack can resolve; `runUnitTest` calls the JS `prepareTestEnvironment()` in `core:testFixtures` to emulate it, so moko resources work in Node tests. A module whose JS tests touch moko resources must apply the moko plugin (it copies the JSON files into the test package).

## Web design system (`:site:designsystem`)

- Kobweb library module holding the web counterparts of `designsystem/androidMain` and the Swift design system: `Web*State` implementations of the shared state interfaces (`uistate/`), Silk/Compose HTML components that render them (`components/`: `ActionButton`/`TextButton(ButtonState)`, `StateText`, `TextBlock`, `Heading`, `Header`, `AppCard`, `TitledCard`, `TextList`, `HorizontalDivider`/`VerticalDivider`, `StateSwitch`/`CheckBox(BooleanState)`, `RadioButton`, `TextField`, `List(ListState)` with empty/error/banner views, `AppTopBar`, `NavigationBar` (sticky translucent header that expands to a full-height menu below a breakpoint) with `NavigationMenuButton`, `ObserveNavigation`, `LanguagePicker`, `ColorModeButton`, `IconButton`, `TextLink`), typography `CssStyle`s with the `Modifier.primary()/secondary()/active()/error()` text colors (the web counterpart of mobile's `TextStyle.secondary()` etc.) and the theme.
- Split like mobile: anything reusable across pages and free of site content (no `SiteRes`, no site assets) belongs in `:site:designsystem` and takes its texts as `StringDesc` parameters; `:site` keeps only site-specific sections, widgets and content. Color text with `.secondary()`/`.active()` rather than `.color(ColorToken.X.themed)`.
- Colors come from `designsystem`'s moko `colors.xml` through `theme/WebColors` (light/dark, like Android's `Colors.kt`). Resolve a `ColorToken` with `ColorToken.themed` (composable) or `ColorToken.resolve(colorMode.webColors())` inside a `CssStyle` — never hardcode a hex color in the site.
- Strings: `WebLocalization` loads one merged moko provider (the app's loader + `DesignSystem` + `CorePresentation`) inside `LocalizedContent(...)` at the app entry; render any `StringDesc` with the composable `localized()`. `AppLanguage` lists the site languages: English, Ukrainian and Polish. The site is not translated into Russian, unlike the apps, so it has no `ru` moko folders and `AppLanguage` has no Russian entry. The language comes from the URL (see **Language URLs** under Site): the layout's `@InitRoute` calls `WebLocalization.show(...)`, which sets `StringDesc.localeType` and `<html lang>`. `LanguagePicker` (a compact EN/UA/PL select) saves the choice in `localStorage` via `WebLocalization.select` and navigates to the same page in that language.
- Not ported yet: pickers (date/time/date-range/money/multi), schedule, business menu, and a notification renderer (`WebNotificationState` exists, nothing displays it). Add them here when a web screen needs them, together with a `Web*State`.

## Site (`:site`)

- Kobweb application module. It may depend on web-target `domain/api` + `domain/impl` modules, `:database`, `:library:cache:*` and `:site:designsystem`, never on feature `data` modules or `presentation`. Build UI from `:site:designsystem` components and states rather than raw HTML/Silk styling.
- Site copy is moko strings in `site/src/commonMain/moko-resources` (`SiteRes`, keys prefixed `site_` so they never collide with the shared modules' keys in the merged provider). The **No string literals in screens** rule applies to the site too, and so does **Translations**, except that the site has only `uk/` and `pl/` siblings (no `ru/`).
- `site/webpack.config.d/moko-resources-inline.js` inlines moko's localization JSON into the bundle, because Kobweb's server serves only `public/` resources and the script, not webpack's emitted assets. moko regenerates `*/webpack.config.d/moko-resources-generated.js` and `*/karma.config.d/moko-resources-generated.js` on each build; they are git-ignored.
- Legal documents (privacy policy `/privacy`, terms `/terms`, data processing agreement `/dpa`) are published texts in `site/legal/<document>/<version>/` (`en.md`, `uk.md`, `pl.md`, `effective-at.txt`), copied from the server repo's `docs/legal/bookkme/` with `site/legal/import.sh` (see `site/legal/README.md`). A published version never changes: `site/legal/published.sha256` locks every file and the `generateLegalTexts` task (plugin `convention.site.legal`) fails the build when a file is edited, deleted or not locked; it also compiles the texts into `publishedLegalTexts`. `/<document>` shows the version in effect (or the first upcoming one) and `/<document>/<version>` a given version, both in the URL's language (`/uk/privacy/<version>`); the older `/<document>/<version>/<language>` URLs redirect to that form. Every page links all three languages and the version history, and links to `https://bookkme.com/...` inside a text open in the text's language. The footer lists only the privacy policy and terms; the DPA is linked from the documents themselves. The footer's description line links the public app (`bookkme-client`) and server (`bookkme`) repositories and the FSL-1.1-ALv2 license (`SiteNavigation.source`).
- **Language URLs**: English lives at unprefixed paths (`/`, `/contact`); every other `AppLanguage` gets its tag as a prefix (`/uk`, `/pl/terms`), built with `AppLanguage.localize(path)` and read back with `AppLanguage.fromPath(path)`. The URL language always wins. An unprefixed URL is sent to the visitor's preferred language (saved picker choice, otherwise the browser languages) by the route interceptor in `routing/LocalizedRoutes.kt` (`LanguageRedirect`), but not during export. Kobweb file routing only knows the English pages, so `LocalizedRoutes.kt` registers the prefixed copy of each `@Page` and `site/build.gradle.kts` lists the static ones in `export { addExtraRoute(...) }`: a new page must be added to both. Internal links go through `WebLocalization.localize(path)`. `PageLayout` emits `<link rel="canonical">` and `rel="alternate" hreflang` for every language plus `x-default` (English) through `HeadLinks`/`LanguageLinks` against `SiteNavigation.ORIGIN`, so the exported HTML carries them; pages with `PageLayoutData(isIndexed = false)` (the 404 page) emit none.
- `/.well-known/security.txt` (RFC 9116) is a static file in `src/jsMain/resources/public/.well-known/`. Its `Policy` links to the security channel on the Contact page (`/contact#security`, the `id` of each `ContactChannel`). The Kobweb server serves dot-directories from `public/` as `text/plain` in both dev and the FULLSTACK export. The `verifySecurityTxt` task (plugin `convention.site.securitytxt`) runs before `jsProcessResources`, so every site build, test run and export fails once `Expires` is less than 30 days away or more than a year ahead. Renew it by moving `Expires` up to a year ahead and redeploying.
- Kobweb version in the catalog must match the Kotlin 2.4 line. The no-comments and block-body rules apply to site code too.

## DOM API

The site links against `kotlinx-browser` instead of `kotlin-dom-api-compat`. DataStore's web storage depends on `kotlinx-browser-js`, a full second copy of the DOM API that cannot be linked next to `dom-api-compat`. `site/build.gradle.kts` therefore excludes `kotlin-dom-api-compat` and depends on `:site:domcompat`. That module adds the one symbol precompiled libraries need but `kotlinx-browser` lacks: moko-resources' `org.w3c.dom.events.EventListener(handler)` factory. Keep the factory in its own module, because a copy inside `:site` creates a circular JS-module import with moko. JS links run with `-Xpartial-linkage-loglevel=ERROR`, so any other missing DOM symbol fails the build instead of the browser. When a library upgrade breaks the link, add the reported symbol to `:site:domcompat`. Upgrading moko-resources does not remove the factory: 0.27.x still calls it.
